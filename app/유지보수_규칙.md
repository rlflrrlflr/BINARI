# 비나리 유지보수 규칙 — AI가 만든 코드를 비개발자가 오래 끌고 가는 법

2026-07-26 작성. **이 문서의 모든 규칙은 실제로 터진 사고에서 역산했다.** 좋아 보이는 원칙은 넣지 않았다.

---

## 0. 문제 정의 — "AI는 단기적"이 아니라 "고장이 조용하다"

AI로 만든 앱의 유지보수 위험은 흔히 "AI가 장기 관점이 없다"로 설명된다. 실제 이 리포에서 관측된 것은 조금 다르다.

**진짜 위험은 고장이 화면에 드러나지 않는다는 것이다.** 비개발자에게 치명적인 건 버그 자체가 아니라 *버그가 조용한 것*이다. 코드를 못 읽으면, 조용한 고장은 영원히 발견되지 않는다.

### 실제 사고 4건 (2026-07-25~26, 한 세션 안에서)

| # | 사고 | 왜 조용했나 | 손실 |
|---|---|---|---|
| 1 | 변수명 `asm`이 GLSL 예약어 → sim 셰이더가 iPhone에서만 컴파일 실패 → 저품질 렌더러로 자동 폴백 | 폴백이 정상 동작처럼 보인다. 개발 환경에선 재현 안 됨 | **사용자가 몇 시간 동안 실행되지도 않는 렌더러를 튜닝** |
| 2 | 같은 상수(`stg`)가 셰이더 2곳에 있는데 한쪽만 수정 | 화면은 뜬다. "뭔가 이상한데" 수준 | 원인 추적에 수십 분 |
| 3 | 일괄 치환이 두 셰이더를 동시에 수정 → sim 컴파일 실패 | 기본 렌더러가 gl이라 아무도 몰랐다 | 발견까지 수 시간 |
| 4 | 사용자가 지금 보는 버전을 알 수 없음 | 앱이 자기 버전을 말하지 않음 | "74야 82야?" 반복, 롤백 4회 |

네 사고의 공통 원인은 **① 침묵하는 실패 ② 진실이 두 곳에 존재**, 단 둘이다.

### 다섯 번째 사고 (2026-07-28) — 새로운 종류

| # | 사고 | 왜 조용했나 | 손실 |
|---|---|---|---|
| 5 | 되물음("무슨 뜻이야"·"어떤 사람인데")을 새 판결로 재처리 → **7연속 HOLD**, 매번 다른 은유만 나감 | **코드는 완벽히 정상 동작했다.** 오류 0, 테스트 26/26 PASS, 화면 정상. 판결이 나가긴 나갔으니 아무 검사도 울리지 않는다 | 유저가 같은 질문을 7번 반복하다 이탈. 판결 7건 전부 미보고 |

이건 앞의 네 건과 종류가 다르다. **코드가 고장난 게 아니라 제품이 고장났다.** 기존 검사는 전부 "코드가 도는가"를 봤지, "나가는 말이 답인가"는 보지 않았다.

대응: 프롬프트의 품질 규칙(제1원칙·되물음 분기·HOLD 남용 금지·응답 스코프)을 **검진의 검사 대상으로 승격**했다(검사 4-2). 규칙이 리팩터링에서 조용히 사라지는 것은 이제 막힌다. 다만 **규칙이 있는지**는 검사할 수 있어도 **규칙이 지켜지는지**는 실모델을 돌려야 알 수 있다 — 그건 `eval/run-eval.mjs`(되물음·S3 문항 포함)의 몫이고, 사람이 CSV를 읽어야 한다.

> **교훈**: 앞으로 "판결이 이상하다"는 제보가 오면 코드부터 보지 말고 **판결 로그의 direction 분포**부터 본다. 한 방향으로 쏠려 있으면 그게 신호다.

### 여섯 번째 사고 (2026-07-28) — 병렬 세션 병합에서만 나는 종류

| # | 사고 | 왜 조용했나 | 손실 |
|---|---|---|---|
| 6 | 콜1 토큰 상한을 320→560으로 올리면서, 그 값으로 콜1/콜2를 가르던 `e2e/verdict.mjs`의 모의 응답을 같이 못 고침 → **폭포수(대체 판결 경로) 검증이 통째로 무력화** | 테스트가 "8/9 PASS"로 나온다. 한 개는 원래 그런가 보다 하고 넘어가기 쉽고, **앱은 실제로 멀쩡했다** | 모바일·클로드앱 유저가 타는 대체 경로가 검증 없이 배포될 뻔함 |

앞의 다섯과 다른 점: **한 세션 안에서는 절대 안 나는 사고다.** 각 세션은 자기 변경 범위 안에서 일관됐고,
병합에도 충돌이 없었다. 어긋난 건 파일이 아니라 **"콜1은 400토큰 이하"라는 서로 다른 세션의 암묵적 전제**였다.

> **교훈 1**: 병합이 깨끗한 것과 결과가 성한 것은 다른 문제다. **병합 후에는 반드시 검진 + 전체 회귀를 다시 돌린다.**
> **교훈 2**: 테스트가 앱을 흉내 낼 때는 **자주 바뀌는 값(토큰 수·타임아웃·픽셀)** 이 아니라 **의미를 담은 표지**로 가른다.
> 검사 5-2가 이걸 강제한다(토큰 수로 가르면 ✗).

## 1. 해법의 원칙 — 코드를 읽게 만들지 말고, 코드가 말하게 만든다

비개발자가 코드를 감사할 수는 없다. 그러니 **감사를 자동화하고, 결과를 한국어 증상으로 출력한다.**

### 사용자가 하는 것: 한 단어

> **"검진"**

AI에게 이렇게 말하면 된다. 명령어도, 터미널도, 사전 준비도 없다.
`/검진` 슬래시 명령으로도 되고, "앱 괜찮아?" "배포해도 돼?" 같은 말로도 걸린다
(`.claude/skills/검진/SKILL.md`에 규칙이 박혀 있어 새 세션도 안다).

직접 돌리고 싶으면 `app/` 폴더에서 `node health-check.mjs`. **빌드도 미리보기 서버도
스크립트가 스스로 준비하고 끝나면 정리한다.** "터미널 하나 더 열고…"라는 안내가
필요해지는 순간, 그건 도구가 실패한 것이다.

> 참고 — **npm**은 자바스크립트 부품(라이브러리) 설치·실행을 맡는 도구다.
> 이 문서에 `npm run …`이 나오면 "그 폴더에서 정해둔 작업을 실행한다"는 뜻일 뿐이고,
> 유지보수를 위해 알아야 할 필요는 없다. 그래서 위 한 단어로 대체했다.

출력은 스택트레이스가 아니라 이렇게 생겼다.

```
✗ 셰이더에 GLSL 예약어를 변수명으로 사용
   무엇이: 1150행: 'asm'
   어떻게: 변수 이름을 바꾸세요. 이 이름들은 일부 기기(특히 iPhone)에서만
          오류를 내고, 그런 기기에서는 수호신이 조용히 저품질 모드로 떨어집니다.
```

**"어떻게"를 그대로 복사해 AI에게 주면 고쳐진다.** 이게 비개발자가 코드를 못 읽어도 유지보수가 되는 이유다.

### 검진이 실제로 잡는가 — 증명됨

사고 3건을 일부러 되살려 검사했다.

| 재현한 사고 | 검진 결과 |
|---|---|
| `kA` → `asm`으로 되돌림 | ✗ 1150행 'asm' 검출 |
| `stg`를 한쪽만 0.45로 변경 | ✗ "0.45 vs 0.68" 검출 |
| AI 고지 문구 삭제 | ✗ "화면 필수 요소 사라짐" 검출 |

그리고 **이 문서를 쓰는 도중 검진이 새 버그를 하나 잡았다.** 튜닝값을 한 곳으로 모으는 리팩터링에서 `TUNE` 블록을 셰이더보다 아래에 두어 초기화 전 참조(TDZ)가 발생 → 앱이 아예 열리지 않는 상태. **빌드는 통과했다.** 검진의 브라우저 검사만이 잡았다.

### 계층 1. 자가진단 — "검진"

무엇을 검사하는가:

| # | 검사 | 왜 |
|---|---|---|
| 1 | GLSL 예약어를 변수로 쓰는가 | 사고 #1 — 특정 기기에서만 터지는 침묵 실패 |

| 7 | **비밀키가 사용자 브라우저로 나갔는가** | 결제·로그인 붙이면 가장 비싼 사고. 지금은 0건 — 그 0을 계속 확인한다 |

| 9 | (브라우저) 실제로 어떤 렌더러가 뜨는가, 화면 오류가 있는가 | 사고 #1·#4. 앱이 안 열리는 사고를 여기서만 잡았다. 검사용 브라우저를 못 켜도 검진 전체가 죽지 않는다(주의로 강등) — 경로가 어긋나면 `CHROME_PATH=/경로` |
| 10 | **배포된 사이트가 지금 살아 있는가** | 1~9는 전부 내 컴퓨터를 본다. 사용자가 보는 건 배포본이다 |

6·7·10번은 **잠들어 있다가 깨어나는 검사**를 포함한다. `package.json`에 DB(Supabase·Firebase 등)나
결제(토스·포트원 등) 라이브러리가 들어오는 순간, 접근 제한(RLS)·금액 서버 검증 검사가 자동으로 켜진다.
결제를 붙인 다음에 보안 점검을 만들면 늦기 때문에 미리 심어 뒀다.

> **규칙**: 새 사고가 나면 고치는 것으로 끝내지 말고 **검사를 하나 추가한다.** 그래야 같은 사고가 두 번 나지 않는다. 이 목록이 길어지는 게 정상이다.

### 계층 2. 단일 진실 원천 — `TUNE` 블록

두 렌더러가 공유하는 튜닝값은 `src/App.jsx`의 `TUNE` 블록 한 곳에만 둔다. 셰이더에는 `${TUNE.stg}` 형태로 주입된다.

```js
const TUNE = {
  stg: 0.68,        // 응집 시차 — 손끝으로 모이는 순서
  starLo: 0.42,     // 별 아닌 입자의 밝기 하한
  starHi: 1.7,      // 별 입자의 밝기 상한(대비)
  nE: 34000,        // 입자 수 — 외향(E)
  nI: 27000,        // 입자 수 — 내향(I)
};
```

효과: 사고 #2(한쪽만 수정)가 **구조적으로 불가능해진다.** 탐지가 아니라 예방이다.

> **주의**: `TUNE`은 반드시 셰이더 정의보다 **위에** 있어야 한다. 아래에 두면 초기화 전 참조로 앱이 안 열린다(위에서 실제로 발생).

### 계층 3. 사용자가 보는 버전 — 배지

화면 우측 하단에 `v98 · 고지 · gl` 형태로 표시된다. 뒤쪽은 **실제로 실행 중인 렌더러**다.

사고 #1·#4가 여기서 걸린다. "지금 뭘 보고 있는지"를 앱이 스스로 말하면, 사용자와 AI가 다른 것을 보며 대화하는 일이 사라진다.

### 계층 4. 결정의 이유 기록 — `변경이력.md`

**무엇을 바꿨나가 아니라 왜 바꿨나를 남긴다.** AI 세션은 이전 대화를 기억하지 못하므로, 이유가 없으면 다음 세션이 같은 것을 되돌린다.

리포에 이미 왕복 사례가 있다: 정령 시각 요소가 v24 제거 → v41 편입 → v68 제거로 세 번 오갔다. 이유가 기록돼 있었으면 한 번에 끝났을 일이다.

### 계층 5. 상시 가동 감시 (사용자가 5분 설정, 무료)

검진은 **돌린 그 순간**만 본다. 새벽 3시에 사이트가 죽으면 아침까지 아무도 모르고,
그동안 들어온 사용자는 전부 잃는다. 이건 코드로 못 막는다 — 밖에서 계속 두드려 줄 사람이 필요하다.

**설정 (한 번만, 콘솔 작업이라 사용자가 직접 눌러야 함)**

1. [uptimerobot.com](https://uptimerobot.com) 가입 (무료 50개까지)
2. `+ New monitor` → **Monitor type**: `HTTP(s)`
3. **URL**: `https://binari-sepia.vercel.app`
4. **Monitoring interval**: `5 minutes`
5. **Alert contacts**: 본인 이메일 체크 (원하면 카톡 대신 SMS/앱 푸시도 무료 플랜에 있음)
6. `Create monitor` — 끝. 사이트가 2회 연속 응답 없으면 메일이 온다.

**같이 켜 두면 좋은 것 (선택)**

- 판결 API도 따로 감시: URL `https://binari-sepia.vercel.app/api/judge`,
  **Monitor type** `Keyword`, keyword `Method Not Allowed`, `Alert when keyword NOT exists`.
  → 사이트는 떠 있는데 **판결만 죽은 상태**를 잡는다. 이게 실제로 더 흔한 고장이다.
- Vercel 대시보드 → 프로젝트 → Settings → Notifications에서 **배포 실패 알림**을 켠다.

**알림이 왔을 때 할 일**: Vercel → Deployments → 직전 정상 배포 → `Promote to Production`.
원인 분석은 사이트를 살린 다음에 한다.

## 3. 코드를 바꿀 때의 절차 (비개발자용)

```
1) "검진"               ← 바꾸기 전 상태 확인(문제가 이미 있으면 먼저 고친다)
2) AI에게 변경 요청
3) "검진"               ← 바꾼 뒤 확인. 빌드·서버는 검진이 알아서 한다
4) AI에게 "스모크도"    ← e2e/smoke.mjs 26개 + e2e/scope-check.mjs 29개(분류기, 1초)
5) 실기기에서 눈으로 확인 ← 헤드리스가 못 잡는 것이 있다
6) "배포"               ← main 푸시 = Vercel 자동배포. 이 말을 하기 전엔 배포되지 않는다
```

**3번에서 ✗가 하나라도 나오면 배포하지 않는다.** '어떻게' 문장을 그대로 AI에게 주면 된다.

## 4. AI 세션에게 요구할 것 (그대로 복사해 쓰세요)

> - 셰이더 상수를 새로 만들지 말고 `TUNE`에 추가해라.
> - 화면 필수 요소(AI 고지·14세 게이트·환불 고지·109 안내·버전 배지)를 지우지 마라.
> - 변경 후 **검진**을 돌리고 결과를 보고해라. ✗가 있으면 배포하지 마라.
> - 새 사고를 고쳤으면 `health-check.mjs`에 그 사고를 잡는 검사를 추가해라.
> - `변경이력.md`에 **왜** 바꿨는지 남겨라.
> - `main` 푸시는 내가 "배포"라고 말했을 때만 해라.

## 5. 결제·로그인을 붙이는 날의 보안 점검표

지금 비나리는 **서버에 사용자 데이터가 없다.** 사주·질문·판결은 전부 브라우저 저장소에만 있고,
API 키는 서버(`api/judge.js`)의 환경변수로만 존재한다(코드에 0건). 그래서 털릴 게 없다.

**결제나 로그인을 붙이는 순간 이 상태가 끝난다.** 아래는 그날 반드시 확인할 것들이고,
①②④는 이미 검진에 심어 두어 라이브러리가 들어오는 순간 자동으로 깨어난다.

| # | 확인할 것 | 안 하면 | 검진이 잡는가 |
|---|---|---|---|
| ① | **행 수준 보안(RLS)을 테이블마다 켰는가** | 남의 사주·질문·판결이 전부 열린다. AI로 만든 앱의 가장 흔한 유출 경로 | ✅ 자동 |
| ② | **서버 전용 키가 브라우저 코드에 없는가** | 키 하나로 DB 전체가 열린다 | ✅ 자동 |
| ③ | 쓰기(insert/update/delete)를 서버(`api/`)를 거치게 했는가 | 브라우저에서 남의 데이터를 지울 수 있다 | △ 경고만 |
| ④ | **결제 금액을 서버에서 다시 검증하는가** | 브라우저에서 금액을 4,900 → 100으로 바꿔 결제된다 | ✅ 자동 |
| ⑤ | 결제 웹훅 서명을 검증하는가 | 가짜 "결제완료" 요청으로 서신을 공짜로 받는다 | ✖ 사람이 확인 |
| ⑥ | 개인정보 항목이 늘었으면 방침을 고쳤는가 | 개인정보보호법 위반. `public/privacy.html` §수집항목 | ✖ 사람이 확인 |
| ⑦ | 결제 전 **환불 불가 고지 + 미리보기**가 결제 화면에 있는가 | 전자상거래법 §17⑥. 청약철회 배제가 무효가 된다 | ✅ (문구 존재만) |

> **원칙**: 돈이나 남의 데이터가 걸린 판단은 **브라우저를 믿지 않는다.** 브라우저에서 오는 값은
> 전부 사용자가 고칠 수 있다고 가정하고, 금액·권한·소유자는 서버에서 다시 계산한다.

## 6. 아직 남은 위험 (숨기지 않고 기록)

| 위험 | 현재 상태 | 다음 조치 |
|---|---|---|
| `App.jsx`가 2,800줄 단일 파일 | 컴포넌트 8 + 셰이더 8 + 사주·천문 함수 33이 한 파일 | 분할은 이득보다 회귀 위험이 커 보류. 검진·TUNE로 위험을 낮춘 상태 |
| 형상 수식이 두 벌(GL_VERT / SHAPE_FN) | 검진이 표류를 탐지 중 | 한 곳으로 합치려면 assemble 로직 차이를 해소해야 한다. 검진이 안전망이므로 급하지 않음 |
| 실모델 판결 품질 | 자동 검사 불가(사람이 읽어야 함) | `app/eval/` 하네스 + 인앱 평가(빗나갔어/글쎄/딱이야) |
| 레이트리밋이 프로세스 메모리 | 서버리스라 인스턴스마다 따로 셈 | Vercel Firewall(콘솔 작업) |
| **S3(몸·병) 넘김이 실모델에서 실제로 되는지 미검증** | 규칙·검사·평가 문항은 넣었으나 실모델 실행을 아직 못 함 | 아래 둘 중 하나로 돌려 자동 플래그 0인지 확인. **배포 전 필수**<br>① `ANTHROPIC_API_KEY=... node eval/run-eval.mjs --cat=S3,REASK`<br>② `node eval/run-eval.mjs --via=https://binari-sepia.vercel.app --cat=S3,REASK` (키 없이 배포본 경유) |
| 되물음 감지가 정규식 | "그래서 뭘 하라는 거야" 류는 잡지만 변형은 놓칠 수 있음 | `reask`·`reask_depth` 계측을 보고 오탐/누락을 조정. 놓쳐도 종전 동작이라 악화는 없음 |
| 유파별 A/B 병렬 해석 보류 | 실재 텍스트 근거 매핑이 없어 채택하지 않음 | 자평진전·삼명통회 원문 매핑을 확보하면 재검토. 근거 없이 "A파/B파"를 붙이는 건 신뢰도를 깎는다 |
| 새벽에 사이트가 죽어도 모름 | 검진은 돌린 순간만 본다 | **계층 5 가동 감시 설정(사용자 5분 콘솔 작업, 미완료)** |
| 개발 도구(vite·esbuild) 취약점 3건 | 빌드에만 쓰이고 사이트에는 실리지 않음 → 방문자 무관 | vite 메이저 업그레이드는 회귀 위험. 급하지 않음. 올릴 땐 검진+스모크 동반 |
| 사업자 상호·번호가 방침에 비어 있음 | 사업자등록 전 | 등록 후 `public/privacy.html`·이용약관에 기입 |

> 이 표를 비워두려 하지 말 것. **남은 위험을 아는 상태가, 모르는 상태보다 안전하다.**

## 팀 공지 — `[팀]` 표시를 언제 붙이나 (2026-07-28 신설)

커밋 제목이 `[팀]` 으로 시작하면 **main 에 올라가는 즉시 디스코드로 알림이 간다.**
붙이지 않은 커밋은 아무 알림도 가지 않고, 매일 아침 리포트의 '어제 앱에 반영된 것'에만 실린다.

### 셋을 **모두** 만족할 때만 붙인다

1. **팀원이 앱을 써보다가 느낄 수 있는 변화인가** — 화면·문구·흐름·판결 내용·모션
2. **자동 검사로는 확인되지 않는가** — 검진·스모크가 잡는 것이면 붙이지 않는다
3. **아침까지 기다리지 말고 지금 확인받아야 하는가**

하나라도 아니면 붙이지 않는다. 애매하면 **붙이지 않는다** — 알림은 적을수록 힘이 세다.

### 왜 전부 알리지 않나
2026-07-28 하루에 main 커밋이 38건 들어왔다(머지 9 · 앱 15 · 문서·도구 14).
전부 알리면 사흘이면 채널을 뮤트하고, 그러면 **판결 실패·앱 오류 알림까지 함께 묻힌다.**
알림이 울리는 순간 "봐야 한다"는 뜻으로 남기려면 우는 횟수를 지켜야 한다.

### 붙이는 예 / 안 붙이는 예

| 커밋 | 붙이나 | 이유 |
|---|---|---|
| 판결을 지표 표에서 뽑게 구조 변경, 몸·건강 질문도 답하게 | ✅ | 판결 내용이 달라진다. 써봐야 안다 |
