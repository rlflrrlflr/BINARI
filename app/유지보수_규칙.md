# 비나리 유지보수 규칙 — AI가 만든 코드를 비개발자가 오래 끌고 가는 법

2026-07-26 작성. **이 문서의 모든 규칙은 실제로 터진 사고에서 역산했다.** 좋아 보이는 원칙은 넣지 않았다.

---

## 0. 문제 정의 — "AI는 단기적"이 아니라 "고장이 조용하다"

AI로 만든 앱의 유지보수 위험은 흔히 "AI가 장기 관점이 없다"로 설명된다. 실제 이 리포에서 관측된 것은 조금 다르다.

**진짜 위험은 고장이 화면에 드러나지 않는다는 것이다.** 비개발자에게 치명적인 건 버그 자체가 아니라 *버그가 조용한 것*이다. 코드를 못 읽으면, 조용한 고장은 영원히 발견되지 않는다.

### 실제 사고 4건 (2026-07-25~26, 한 세션 안에서)

| # | 사고 | 왜 조용했나 | 손실 |
|---|---|---|---|
| 1 | 변수명 `asm`이 GLSL 예약어 → sim 셰이더가 iPhone에서만 컴파일 실패 → 저품질 렌더러로 자동 폴백 | 폴백이 정상 동작처럼 보인다. 개발 환경에선 재현 안 됨 | **사용자가 몇 시간 동안 실행되지도 않는 렌더러를 튜닝** |
| 2 | 같은 상수(`stg`)가 셰이더 2곳에 있는데 한쪽만 수정 | 화면은 뜬다. "뭔가 이상한데" 수준 | 원인 추적에 수십 분 |
| 3 | 일괄 치환이 두 셰이더를 동시에 수정 → sim 컴파일 실패 | 기본 렌더러가 gl이라 아무도 몰랐다 | 발견까지 수 시간 |
| 4 | 사용자가 지금 보는 버전을 알 수 없음 | 앱이 자기 버전을 말하지 않음 | "74야 82야?" 반복, 롤백 4회 |

네 사고의 공통 원인은 **① 침묵하는 실패 ② 진실이 두 곳에 존재**, 단 둘이다.

### 다섯 번째 사고 (2026-07-28) — 새로운 종류

| # | 사고 | 왜 조용했나 | 손실 |
|---|---|---|---|
| 5 | 되물음("무슨 뜻이야"·"어떤 사람인데")을 새 판결로 재처리 → **7연속 HOLD**, 매번 다른 은유만 나감 | **코드는 완벽히 정상 동작했다.** 오류 0, 테스트 26/26 PASS, 화면 정상. 판결이 나가긴 나갔으니 아무 검사도 울리지 않는다 | 유저가 같은 질문을 7번 반복하다 이탈. 판결 7건 전부 미보고 |

이건 앞의 네 건과 종류가 다르다. **코드가 고장난 게 아니라 제품이 고장났다.** 기존 검사는 전부 "코드가 도는가"를 봤지, "나가는 말이 답인가"는 보지 않았다.

대응: 프롬프트의 품질 규칙(제1원칙·되물음 분기·HOLD 남용 금지·응답 스코프)을 **검진의 검사 대상으로 승격**했다(검사 4-2). 규칙이 리팩터링에서 조용히 사라지는 것은 이제 막힌다. 다만 **규칙이 있는지**는 검사할 수 있어도 **규칙이 지켜지는지**는 실모델을 돌려야 알 수 있다 — 그건 `eval/run-eval.mjs`(되물음·S3 문항 포함)의 몫이고, 사람이 CSV를 읽어야 한다.

> **교훈**: 앞으로 "판결이 이상하다"는 제보가 오면 코드부터 보지 말고 **판결 로그의 direction 분포**부터 본다. 한 방향으로 쏠려 있으면 그게 신호다.

## 1. 해법의 원칙 — 코드를 읽게 만들지 말고, 코드가 말하게 만든다

비개발자가 코드를 감사할 수는 없다. 그러니 **감사를 자동화하고, 결과를 한국어 증상으로 출력한다.**

```
npm run 검진
```

이 한 줄이 전부다. 출력은 스택트레이스가 아니라 이렇게 생겼다.

```
✗ 셰이더에 GLSL 예약어를 변수명으로 사용
   무엇이: 1150행: 'asm'
   어떻게: 변수 이름을 바꾸세요. 이 이름들은 일부 기기(특히 iPhone)에서만
          오류를 내고, 그런 기기에서는 수호신이 조용히 저품질 모드로 떨어집니다.
```

**"어떻게"를 그대로 복사해 AI에게 주면 고쳐진다.** 이게 비개발자가 코드를 못 읽어도 유지보수가 되는 이유다.

### 검진이 실제로 잡는가 — 증명됨

사고 3건을 일부러 되살려 검사했다.

| 재현한 사고 | 검진 결과 |
|---|---|
| `kA` → `asm`으로 되돌림 | ✗ 1150행 'asm' 검출 |
| `stg`를 한쪽만 0.45로 변경 | ✗ "0.45 vs 0.68" 검출 |
| AI 고지 문구 삭제 | ✗ "화면 필수 요소 사라짐" 검출 |

그리고 **이 문서를 쓰는 도중 검진이 새 버그를 하나 잡았다.** 튜닝값을 한 곳으로 모으는 리팩터링에서 `TUNE` 블록을 셰이더보다 아래에 두어 초기화 전 참조(TDZ)가 발생 → 앱이 아예 열리지 않는 상태. **빌드는 통과했다.** 검진의 브라우저 검사만이 잡았다.

## 2. 유지보수 4계층

### 계층 1. 자가진단 — `npm run 검진`

무엇을 검사하는가 (전부 실제 사고 기반):

1. **GLSL 예약어를 변수로 쓰는가** — 특정 기기에서만 터지는 사고 차단
2. **같은 설정값이 두 곳에서 어긋났는가** — 표류 탐지
3. **같은 수식을 두 벌 유지하는가** — 표류의 원인을 눈에 보이게
4. **화면 필수 요소가 사라졌는가** — AI 고지·14세 게이트·환불 고지·위기 안내(109)·버전 배지
4-2. **판결이 흐려지는 것을 막는 규칙이 살아 있는가** — 제1원칙·되물음 분기·HOLD 남용 금지·응답 스코프(S1·S2·S3)·S3 넘김 절차·scope 계측·콜1 scope 필드·카드 앞면 용어(사고 #5 기반)
5. **평가 도구가 앱과 같은 것을 재는가** — 채점이 실제 앱과 무관해지는 사고 차단(판돈 태그·되물음 태그·scope 필드 3종 대조)
6. **빌드 산출물 존재**
7. **(브라우저) 실제로 어떤 렌더러가 뜨는가, 화면 오류가 있는가** — 검사용 브라우저를 못 켜면 검진 전체가 죽던 것을 고쳤다(주의로 강등). 브라우저 경로가 어긋나면 `CHROME_PATH=/경로 npm run 검진`

> **규칙**: 새 사고가 나면 고치는 것으로 끝내지 말고 **검사를 하나 추가한다.** 그래야 같은 사고가 두 번 나지 않는다. 이 목록이 길어지는 게 정상이다.

### 계층 2. 단일 진실 원천 — `TUNE` 블록

두 렌더러가 공유하는 튜닝값은 `src/App.jsx`의 `TUNE` 블록 한 곳에만 둔다. 셰이더에는 `${TUNE.stg}` 형태로 주입된다.

```js
const TUNE = {
  stg: 0.68,        // 응집 시차 — 손끝으로 모이는 순서
  starLo: 0.42,     // 별 아닌 입자의 밝기 하한
  starHi: 1.7,      // 별 입자의 밝기 상한(대비)
  nE: 34000,        // 입자 수 — 외향(E)
  nI: 27000,        // 입자 수 — 내향(I)
};
```

효과: 사고 #2(한쪽만 수정)가 **구조적으로 불가능해진다.** 탐지가 아니라 예방이다.

> **주의**: `TUNE`은 반드시 셰이더 정의보다 **위에** 있어야 한다. 아래에 두면 초기화 전 참조로 앱이 안 열린다(위에서 실제로 발생).

### 계층 3. 사용자가 보는 버전 — 배지

화면 우측 하단에 `v98 · 고지 · gl` 형태로 표시된다. 뒤쪽은 **실제로 실행 중인 렌더러**다.

사고 #1·#4가 여기서 걸린다. "지금 뭘 보고 있는지"를 앱이 스스로 말하면, 사용자와 AI가 다른 것을 보며 대화하는 일이 사라진다.

### 계층 4. 결정의 이유 기록 — `변경이력.md`

**무엇을 바꿨나가 아니라 왜 바꿨나를 남긴다.** AI 세션은 이전 대화를 기억하지 못하므로, 이유가 없으면 다음 세션이 같은 것을 되돌린다.

리포에 이미 왕복 사례가 있다: 정령 시각 요소가 v24 제거 → v41 편입 → v68 제거로 세 번 오갔다. 이유가 기록돼 있었으면 한 번에 끝났을 일이다.

## 3. 코드를 바꿀 때의 절차 (비개발자용)

```
1) npm run 검진          ← 바꾸기 전 상태 확인(문제가 이미 있으면 먼저 고친다)
2) AI에게 변경 요청
3) npm run build
4) npm run preview       ← 다른 터미널
5) npm run 검진          ← 바꾼 뒤 확인
6) node e2e/smoke.mjs    ← 26개 시나리오
6-2) node e2e/scope-check.mjs  ← 스코프·되물음 분류기 29개(브라우저 불필요, 1초)
7) 실기기에서 눈으로 확인 ← 헤드리스가 못 잡는 것이 있다
```

**5번에서 ✗가 하나라도 나오면 배포하지 않는다.** '어떻게' 문장을 그대로 AI에게 주면 된다.

## 4. AI 세션에게 요구할 것 (그대로 복사해 쓰세요)

> - 셰이더 상수를 새로 만들지 말고 `TUNE`에 추가해라.
> - 화면 필수 요소(AI 고지·14세 게이트·환불 고지·109 안내·버전 배지)를 지우지 마라.
> - 변경 후 `npm run 검진`을 돌리고 결과를 보고해라. ✗가 있으면 배포하지 마라.
> - 새 사고를 고쳤으면 `health-check.mjs`에 그 사고를 잡는 검사를 추가해라.
> - `변경이력.md`에 **왜** 바꿨는지 남겨라.

## 5. 아직 남은 위험 (숨기지 않고 기록)

| 위험 | 현재 상태 | 다음 조치 |
|---|---|---|
| `App.jsx`가 2,800줄 단일 파일 | 컴포넌트 8 + 셰이더 8 + 사주·천문 함수 33이 한 파일 | 분할은 이득보다 회귀 위험이 커 보류. 검진·TUNE로 위험을 낮춘 상태 |
| 형상 수식이 두 벌(GL_VERT / SHAPE_FN) | 검진이 표류를 탐지 중 | 한 곳으로 합치려면 assemble 로직 차이를 해소해야 한다. 검진이 안전망이므로 급하지 않음 |
| 실모델 판결 품질 | 자동 검사 불가(사람이 읽어야 함) | `app/eval/` 하네스 + 인앱 평가(빗나갔어/글쎄/딱이야) |
| 레이트리밋이 프로세스 메모리 | 서버리스라 인스턴스마다 따로 셈 | Vercel Firewall(콘솔 작업) |
| **S3(몸·병) 넘김이 실모델에서 실제로 되는지 미검증** | 규칙·검사·평가 문항은 넣었으나 실모델 실행은 API 키가 없어 못 돌림 | `ANTHROPIC_API_KEY=... node eval/run-eval.mjs --cat=S3,REASK` 를 돌려 자동 플래그 0인지 확인. **배포 전 필수** |
| 되물음 감지가 정규식 | "그래서 뭘 하라는 거야" 류는 잡지만 변형은 놓칠 수 있음 | `reask`·`reask_depth` 계측을 보고 오탐/누락을 조정. 놓쳐도 종전 동작이라 악화는 없음 |
| 유파별 A/B 병렬 해석 보류 | 실재 텍스트 근거 매핑이 없어 채택하지 않음 | 자평진전·삼명통회 원문 매핑을 확보하면 재검토. 근거 없이 "A파/B파"를 붙이는 건 신뢰도를 깎는다 |

> 이 표를 비워두려 하지 말 것. **남은 위험을 아는 상태가, 모르는 상태보다 안전하다.**
