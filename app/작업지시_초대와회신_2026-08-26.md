## 0. 왜 지금인가 — 「분모 100 이후」에서 당겨온 근거

`역할과초대 §F`가 초대 레그를 **분모 100 이후**로 미뤄뒀다. 사유는 *"모수 14에서는 좋은 안인지 판별이 안 된다"*였다. 그 판단을 뒤집는 게 아니라 **구분한다**:

- 미룬 것은 **평가**의 문제였다. 이 건은 **존재**의 문제다 — 방향점검 2026-08-26의 결론대로 **분모가 100이 와도 공유 게이트는 0을 잰다.** 우리 공유물이 1인 완결 이미지형이라 받은 사람이 아무것도 안 해도 루프가 닫히고, k의 분자를 만드는 장치가 아예 없다. **없는 루프는 표본을 늘려도 못 잰다.**
- **B의 랜딩이 곧 공유 유입 온보딩 축약**이다(`루프배관 §1-2`). 미뤄둔 두 과제가 한 작업이다. 현행 공유 유입 완주율 40%(하한 40·합격선 50)의 유력 병목이 장면 10·탭 10인데, 「생일 3칸」 랜딩이 그 병목을 정면으로 지난다.
- 개발 라인(창업자+AI)은 소재 제작(팀 몫)과 병렬이라 크리티컬 패스를 안 먹는다.

⚠ **광고 집행일은 이 지시서의 범위가 아니다**(창업자: "아직 논의할 게 아니야"). 착수 순서만 정하고 집행일과 엮지 않는다.

## 1. 순서 — 이 순서를 바꾸지 마라

```
① 처리방침 개정 + 검사 갱신   ← 코드보다 먼저
② /api/invite + 저장소(메모리 폴백 포함)
③ B 랜딩 화면 + 곁 승격
④ 계측·게이트 정의
```

**왜 처리방침이 먼저인가**: 지금 유저 화면에 두 문장이 떠 있다.
- `privacy.html` §5-1 — *"저희 서버에 저장하지 않습니다"*
- `privacy.html` §보안 — *"사주 프로필·판결 기록은 서버에 저장하지 않고 이용자 기기(브라우저)에만 보관합니다"*

저장을 붙이는 순간 이 문장이 거짓이 된다. 이 리포엔 이미 그 종류의 사고가 있었다 — **v127.7: 약속을 먼저 쓰고 코드가 안 따라갔다.** 이번은 반대 방향(코드가 먼저 가고 약속이 낡는)이고 결과는 같다. `e2e/privacy-check.mjs`(113항목)가 이 문장들을 지키고 있을 수 있으므로 **검사부터 확인**할 것.

## 2. 처리방침 개정안

### 2-1. §5-1은 **고치지 않는다** (중요)

*"판결 공유 링크는 서버에 저장하지 않습니다"*는 **여전히 참**이다. 판결 공유(`?v=…`)와 초대 링크는 다른 물건이다. 이 문장을 건드리면 사실이던 것까지 흐려진다. → **새 절을 만든다.**

### 2-2. 새 절 §5-2 「초대 링크 — 둘 사이를 함께 보기」

담을 내용(문안은 로직 세션이 다듬되 항목은 빠짐없이):

| 항목 | 내용 |
|---|---|
| **저장하는 것** | 초대를 보낸 이용자의 **관계 계산용 파생값**(일간·일지·오행·해자리·달자리·웨톤·촐킨·납음·수) · 응답 여부와 시각 · 받은 이가 동의한 경우에 한해 표시용 이름 |
| **저장하지 않는 것** | **생년월일·태어난 시각 원값**, 질문, 판결문, 서신, 각인·궁합 문서 |
| **보관 기간** | **30일 후 자동 삭제**(저장소 TTL로 강제 — 코드가 아니라 인프라 수준) · 응답이 끝난 초대는 그 시점에 닫힘 |
| **제3자 제공** | 받은 이가 **답했다는 사실**이 보낸 이의 「곁」에 표시됨 → **별도 동의**를 받는다(체크). 동의하지 않으면 받은 이는 결과를 보되 보낸 이에게는 아무것도 가지 않는다 |
| **이용자 권리** | 보낸 이는 초대를 **취소**할 수 있고, 취소하면 즉시 삭제된다 |
| **정직한 고지 1** | *"초대를 받은 사람은 네 명식 값을 보게 돼 — 생년월일 자체는 전해지지 않지만, 그 값들로 되짚을 수는 있어."* |
| **정직한 고지 2** | 링크는 **한 번만 응답**되고 만료된다 — 다시 퍼뜨려도 다른 사람은 열지 못한다 |

**정직한 고지 1을 왜 반드시 넣나** — 방향점검 2026-08-26이 새로 잡은 것: 우리 설계 열쇠였던 *"사이 값은 역산되지 않는다(미지수 둘, 방정식 하나)"*는 **제3자에게만 참이다.** 상대는 자기 값을 알므로 미지수가 하나가 되어 **보낸 이의 값을 풀 수 있는 유일한 사람**이 된다. 헌장의 판단 기준이 「유저가 무엇이 나가는지 보고 있는가」이므로 숨기지 말고 **보이게** 내보낸다.

### 2-3. §보안 「저장 최소화」 줄 갱신

*"사주 프로필·판결 기록은 서버에 저장하지 않고…"*는 유지하되 단서를 붙인다 — *"단 초대를 보낸 경우, 관계 계산에 필요한 파생값만 30일간 보관합니다(§5-2)."*

## 3. `/api/invite` 명세

```
POST   /api/invite          body { axes }                    → { id }
       A가 초대를 만든다. axes 는 A 기기에서 계산한 파생값만(생일 아님).

GET    /api/invite?ids=…    (쉼표 구분, 최대 24)             → [{ id, answered, label, at }]
       A가 앱을 열 때 자기 초대들의 상태를 확인한다. 곁 승격의 유일한 입력.

POST   /api/invite/answer   body { id, bAxes, notify, label } → { aAxes }
       B가 생일을 넣는다. 서버는 A의 axes 를 돌려주고 계산은 B 기기(match.js)에서 한다.
       notify=false 면 answered 를 기록하지 않는다 — 동의가 진짜 선택지여야 한다.
       ⚠ 이미 answered 인 초대는 거절(410). 응답 1회 + 만료가 재공유 방어다.

DELETE /api/invite/:id                                        → ok
       A의 취소 = 즉시 삭제(처리방침의 이용자 권리).
```

**계산을 B 기기에서 하는 이유**: `match.js`는 네트워크 호출 0의 순수 함수다. 서버로 옮기면 같은 로직이 두 벌이 되고, 이 리포가 반복해서 겪은 사고가 정확히 그것이다(*"베끼면 같은 사람을 두고 다른 말을 하게 된다"*).

**저장소**: Vercel KV(Upstash). Supabase가 아닌 이유 셋 — ①TTL이 네이티브라 보관기간이 인프라에서 강제된다(처리방침에 정직하게 쓸 수 있다) ②계정이 없으니 관계형이 과하다 ③REST를 `fetch` 로 직접 부르면 **의존성 추가 0개**다(현재 deps 3개인 절제를 지킨다). Supabase는 ROADMAP 2단계 *"결제가 기기 간 정체성을 요구하는 첫 순간"* 자리에 그대로 둔다.

> ⚠ **환경변수가 없으면 프로세스 메모리로 돈다.** 창업자의 KV 프로비저닝을 기다리지 말고 인터페이스를 먼저 짜서 개발·검사를 끝낸다. `api/judge.js` 의 `_hits` Map 이 같은 패턴이고, 그 주석이 한계(인스턴스당·휘발)까지 이미 적어 뒀다 — **같은 한계를 주석에 명기**할 것.

## 4. B 랜딩 화면 (= 공유 유입 온보딩 축약)

```
① 누가 불렀는지 한 줄        "○○이 너와의 사이를 궁금해했어."   (이름은 A가 적어둔 것)
② 생일 3칸 (+시 선택)        온보딩 전체를 밟게 하지 않는다 — 이게 §1-2 축약이다
③ 무엇이 나가는지 고지        "네 생일은 이 기기에만. ○○에게는 '답했다'만 전해져(선택)."
④ 동의 체크 1개              "답했다는 걸 ○○에게 알려도 될까?"  ← 끄면 A에겐 아무것도 안 감
⑤ 결과 — 둘 사이 아홉 축      v137 chorus 머리 그대로(갈림을 먼저)
⑥ 다음 문 하나               "네 수호신도 만들어볼래?"          ← k 의 분자
```

**⑥이 이 지시서의 목표다.** B는 이미 생일을 넣어 온보딩에서 제일 무거운 칸을 통과한 상태다 — 현행 공유 랜딩(판결 카드만 보고 처음부터 온보딩)보다 구조적으로 짧다.

**⑤에서 총점을 만들지 않는다**(match.js 파일 머리 원칙 그대로). 갈림이 알맹이고, 평균을 내면 그게 사라진다.

## 5. 곁 승격

- A가 앱을 열면 `GET /api/invite?ids=…` 로 확인 → 답이 온 초대의 상대를 `GY_CALLED` → `GY_STANDING` 으로 올린다. 렌더는 **이미 갈라져 있다**(`dim` 1 vs 0.45, 궤도 앞줄, 목록 className).
- **숫자·배지·개수를 붙이지 않는다.** 승격은 **밝기와 자리로만** 말한다(곁탭IA §5). "N명이 답했어" 같은 문장이 붙는 순간 명부가 카운터가 된다.
- 초대 id 목록은 A 기기 localStorage 에 둔다(상한은 곁 상한 24와 맞춘다).

## 6. 계측·게이트 (데이터 레인)

| 이벤트 | 언제 | 속성 |
|---|---|---|
| `invite_created` | A가 초대 생성 | `from`(match/gyeot) |
| `invite_opened` | B가 링크를 열고 **유효 검증 통과** | 위조·만료는 세지 않는다(공유 수신 계측이 이미 같은 규칙) |
| `invite_answered` | B가 생일 제출 | `notify`(동의 여부) |
| `invite_to_onboard` | B가 자기 수호신 만들기로 진입 | **← k의 분자** |
| `gyeot_promoted` | A 확인으로 승격 | 지연 시간(초대→확인) |

**게이트 이름을 새로 판다**: 기존 `k ≥ 1.0`(공유 1건당 유입)과 **분자가 다르다.** `§2-D 규칙 4`가 이미 *"분자가 다르면 별개 지표 — 이름을 가른다"*를 못 박았으므로 **초대 응답률**(`invite_answered / invite_created`)과 **초대발 유입률**(`invite_to_onboard / invite_created`)로 따로 세운다. 수치 목표는 **분모 100 이후에 정한다** — 지금 숫자를 박으면 근거 없는 게이트가 하나 더 생긴다.

## 7. 지키는 선 (헌장 대조 — 착수 전 읽을 것)

| 헌장 | 어떻게 지키나 |
|---|---|
| **모를 권리(판결 국면)** | 초대는 A가 당겨서 만든다. "답이 왔어"는 **앱을 열었을 때 곁 탭에서** 보인다 — push 아님. 알림·배지 금지 |
| **실명은 안 나간다** | 서버에 B의 생년월일 원값 없음. 이름은 A가 적어둔 것이거나 B가 동의해 준 것 |
| **미동의 제3자** | B는 **본인이 직접 입력**한다(본인 제공). A에게 가는 것은 **동의 체크가 켜졌을 때만** |
| **개수·순위 금지** | 승격은 밝기·자리로만. 숫자 0개 |
| **역산** | A의 axes 가 B에게 감 — **고지한다**(§2-2). 제3자에게는 안 감(응답 1회 + 30일 만료) |
| **정보가 나가는 경로** | 판단 기준은 「유저가 무엇이 나가는지 보고 있는가」. 이 지시서의 모든 고지가 그 기준을 통과하려고 있다 |

## 8. 창업자 몫 (AI가 못 하는 일)

1. **Vercel KV(Upstash) 생성** → 환경변수(`KV_REST_API_URL`·`KV_REST_API_TOKEN` 류) 설정 → **수동 Redeploy**(환경변수는 자동배포로 안 붙는다 — CLAUDE.md 운영 규칙)
2. 배포 후 확인 한 줄: 초대를 하나 만들고, 다른 기기(또는 시크릿 창)에서 링크를 열어 생일을 넣은 뒤, 원래 기기에서 앱을 열어 **곁이 밝아지는지** 본다. 이게 이 기능의 유일한 완주 검사다.

## 10. 안 하는 것 (범위 밖 — 늘리지 마라)

- **개인별 홈페이지(`/n/{slug}` 류)** — 안 만든다. 곁 탭이 이미 그 자리고, 공개 색인은 우리 robots.txt 정책(쿼리스트링 수집 차단)과 정면 충돌하며, 공개 지도는 개수·순위 금지와 부딪힌다. 사주도령이 개인 페이지를 쓰는 건 **앱이 없어서**다.
- **푸시·알림** — 재방문 지표 판정 전까지 보류(작업지시_법정고지 그대로). A는 앱을 열어야 답을 본다. 그게 D7 게이트의 정직한 측정 환경이다.
- **B의 값을 A에게 보내기** — 「답이 왔어」 한 비트만. B의 명식이 A에게 가는 순간 제3자 제공의 무게가 완전히 달라진다.
- **초대에 역할 라벨 동봉** — `아홉축역할설계 §⑤ 위험 4` 실측: 카드에 역할을 동봉하면 유출이 5.6~6.5bit 로 올라 위험선 이하 쌍이 3.7~6.3% 생긴다. 별도 게이트를 만들기 전에는 붙이지 않는다.
- **광고 집행일과 엮기** — 창업자 지시로 범위 밖.
