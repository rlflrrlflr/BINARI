## 2. 코드 세션 — 배관 A·B (반나절 이내)

### A. 판결 공유가 조용히 죽는다 〔최우선〕

판결 공유 핸들러가 이렇다.

```js
try {
  if (navigator.share) { await navigator.share({ ... }); return; }
} catch (_) { return; }          // ← 여기
try { await navigator.clipboard.writeText(...); setShared(true); ... } catch (_) {}
```

**`catch` 안의 `return` 이 클립보드 폴백을 막는다.**
- `navigator.share` **자체가 없으면**(안드로이드 웹뷰 등) 폴백으로 잘 내려간다.
- 그런데 **있는데 실패하면**(인앱 브라우저에서 흔하다) `catch` 로 들어가 **그대로 끝난다.**
- 유저 화면에는 **아무 반응이 없다.** 눌렀는데 아무 일도 안 일어난다.

**고칠 것**
1. `catch` 에서 **취소(`AbortError`)만 조용히 끝내고**, 나머지 실패는 **클립보드 폴백으로 내려보낸다.**
   (카드 저장 쪽 `saveOrShareCard()` 는 이미 그렇게 하고 있다 — **같은 파일 안에 올바른 예가 있다.**)
2. **계측을 붙인다** — `verdict_share_attempted`(경로: share/clipboard) 와 `verdict_share_failed`(사유).
   지금은 성공만 세므로 **0이 「안 보냈다」인지 「못 보냈다」인지 영영 모른다.** 이게 이 지시서의 핵심이다.
3. 클립보드마저 막히면 **주소를 화면에 띄워 직접 복사하게** 한다. 막다른 길을 만들지 않는다.

### B. 카드 저장 — 실패를 성공으로 센다

`saveOrShareCard()` 가 이렇게 끝난다.

```js
if (!iOS) { a.click(); a.remove(); done("download"); }        // ← 눌렀을 뿐, 저장은 확인 안 함
else { const w = window.open(...); ... done("new_tab"); }      // ← 팝업이 막혀도 done
```

- `done()` 은 `card_saved` 를 찍는데 **실제 저장 여부를 확인하지 않는다.**
- 안드로이드 인앱 웹뷰는 `a.download` 를 무시하고, 인앱 브라우저는 **`data:` 주소로의 최상위 이동을 막는다**(크롬·웹킷·엣지 전부).
- iOS 경로는 `window.open` 인데 **인앱에서 팝업이 막힌다.** `w` 가 `null` 이면 `location.href = dataUrl` 로 가는데 **그것도 막힌다.**

**실측이 같은 방향이다** — 저장 성공 기록이 **전부 일반 브라우저**고, 카카오 인앱에서 부적을 연 사람의 저장은 0건이다.

**고칠 것**
1. **`data:` 대신 `blob:` 주소**를 쓴다(`URL.createObjectURL`). 같은 파일 988행에 이미 그 방식이 있다.
2. **iOS 경로를 새 탭에서 「화면 안 이미지」로 바꾼다** — 페이지 안에 큰 이미지를 띄우고 **「길게 눌러 저장」** 안내를 붙인다. 새 창을 안 열면 막힐 일이 없다.
3. **안드로이드 폴백도 같은 화면**을 쓴다. 내려받기가 안 되면 같은 이미지를 보여준다.
4. **`done()` 을 「실제로 내보낸 것」에만 붙이고**, 못 한 경로에는 `card_save_failed{way, reason}` 를 찍는다.
5. 검사(`app/e2e/`)에 케이스 하나 — **공유시트를 없애고 팝업을 막은 상태에서, 유저가 눈으로 볼 수 있는 결과가 나오는가.**

⚠ **판정 기준**: 「저장이 됐는가」를 코드가 확신할 수 없는 경로에서는 **성공으로 세지 않는다.** 지금 그 반대다.

## 4. 디자인 세션 — 단톡방에서 눈에 띄게 (배관 C)

**카톡·인스타에 링크를 붙이면 모두에게 똑같은 그림이 뜬다.** 링크에 판결이 실려 있는데 미리보기는 공용 이미지다.
**단톡방에 던져도 아무도 누를 이유가 없는 자리가 여기다.**

1. **미리보기 이미지를 판결별로 다르게 만든다.**
   ⚠ **주소에 파생값을 그냥 실으면 서버 기록에 남는다.** 서명 경로(`api/share.js`)가 이미 있으니 **그 경로를 재사용할 수 있는지부터 본다.**
   ⚠ **실명은 절대 안 싣는다.** 판정은 `shareRisk()` 를 통과해야 한다.
2. **최소안부터**: 판결어(GO/STOP/HOLD)와 수호신만 바뀌어도 「무엇이 왔는지」가 보인다. 질문 원문은 안 넣는다.
3. **카드가 단톡방에서 어떻게 보이는지** 실제 화면으로 확인한다 — 지금 세로 1080×1920인데 카톡 목록에서는 잘린다.

## 5. 전략 세션 — 한 장이 여러 명에게 닿게

**링크 한 장당 열람이 1.07회다.** 한 장에 24명까지 답할 수 있게 만들어 놨는데 1:1로만 보낸다.
**받는 쪽 전환은 이미 좋다(연 8명 중 6명이 답함, 75%). 문제는 보내는 쪽이다.**

1. **뿌리는 화면의 문구를 「한 사람에게」가 아니라 「단톡방에」 전제로 다시 쓴다.** 고지 문구는 이미 있다.
2. **초대를 만드는 문을 판결 직후로 옮기는 것을 검토한다** — 지금은 곁 탭 안쪽에 숨어 있고, 판결 본 9명 중 초대를 만든 사람이 1명이다.
3. **각인을 공유 단위로 올리는 것을 검토한다** — 판결 본 9명이 **전원** 눌렀고 **모델을 안 불러 원가가 0원**이다. 지금 공유 배선이 판결보다 약하다.

⚠ **하지 말 것 — 「하루 10회 넘으면 친구를 부르면 더 물어볼 수 있어」는 폐기됐다.**
판결 천장 지시서(8/30)에 창업자 발언 원문이 있다 — *「추가 질문하고 싶어하는 사람이 얼마나 되나 체크해보자」*.
**재는 게 목적이고 막는 게 목적이 아니다.** 그리고 같은 지시서가 *「초대는 유일한 유입 루프이므로 거기 통행료를 걸면 우리 손으로 분자를 줄인다」*고 이미 적어 놨다.
**화면 천장은 막지 않고 통과시키며 의사만 잰다. 서버 상한(비용 방어)만 살린다.**
